# اسکریپت ارائه برای مدیریت ارشد

## عنوان ارائه

# پلتفرم حسابداری هوشمند
## معماری، ایجنت‌ها، ارز و نقشه‌راه اجرا

**مدت پیشنهادی:** ۱۵ دقیقه
**هدف جلسه:** تصویب اصول معماری و اولویت‌های مرحلهٔ بعد؛ نه تصویب Migration یا اتصال مالیاتی

## اسلاید ۱ — مسئلهٔ کسب‌وکار

**متن روی اسلاید:**

- چند باجه و چند کاربر هم‌زمان
- ثبت خرید، هزینه و سند حسابداری
- دفترهای قابل ردیابی
- کنترل هوشمند بدون توقف بی‌دلیل کاربر
- آمادگی برای ارز، واردات، صادرات و Compliance

**متن گوینده:**

هدف ما ساخت یک فرم ثبت سند دیگر نیست. هدف، ایجاد یک پلتفرم حسابداری است که بتواند ورود اطلاعات روزانه، کنترل حسابداری، گزارش‌گیری، انطباق و حسابرسی را در یک زنجیرهٔ قابل ردیابی به هم متصل کند. کاربر باجه باید بتواند سریع کار کند؛ مدیر مالی نیز باید بداند هر سند چه کسی، چه زمانی و بر اساس کدام منبع ثبت و بررسی شده است.

## اسلاید ۲ — سه اصل تصمیم‌گیری

**متن روی اسلاید:**

۱. ثبت کاربر با ثبت قطعی حسابداری یکی نیست.
۲. هشدار هوشمند با خطای قطعی Domain یکی نیست.
۳. سند Posted قابل ویرایش مستقیم نیست.

**متن گوینده:**

اگر این سه اصل رعایت نشوند، هوش مصنوعی یا سرعت ثبت را قربانی می‌کند یا کنترل مالی را ضعیف. سند می‌تواند ذخیره شود و اخطار تکمیل بگیرد، اما فقط توازن، دوره، دسترسی و قواعد قطعی Domain حق توقف Posting را دارند.

## اسلاید ۳ — آنچه از OSS آموختیم

**متن روی اسلاید:**

- ERPNext: Company، سند منبع، دفترکل، کنترل دوره و Reversal
- Frappe Books: تجربهٔ ساده و گزارش‌های قابل فهم
- Blnk: مقدار دقیق، نرخ، Reference، وضعیت تراکنش و Reconciliation
- نتیجه: اقتباس الگو، نه کپی کد

**متن گوینده:**

ERPNext به ما می‌آموزد که سند عملیاتی و اثر دفترکل باید قابل ردیابی باشند. Frappe Books سادگی فرم و گزارش را برجسته می‌کند. Blnk برای مقدار دقیق و تراکنش‌های مالی الگوی خوبی است. اما مقررات ایران، RLS، ریال/تومان و ساختار سازمانی ما باید در معماری خودمان تعریف شود.

## اسلاید ۴ — معماری پیشنهادی

**متن روی اسلاید:**

```text
Domain → Application → Infrastructure → Presentation
                         ↓
                    Agent Runtime
```

**متن گوینده:**

Domain قواعد ثابت حسابداری را مستقل نگه می‌دارد. Application چرخهٔ Use Case و مجوزها را اجرا می‌کند. Infrastructure مسئول Supabase، صف، فایل و پشتیبان است. Presentation فرم و گزارش را نشان می‌دهد. Agent Runtime از Event و Read Model می‌خواند و یافته تولید می‌کند؛ به سند Posted دسترسی ویرایشی ندارد.

## اسلاید ۵ — ثبت هم‌زمان چند باجه

**متن روی اسلاید:**

```text
Draft → Validate → Submit → Approve → Post
```

- Idempotency Key
- شمارهٔ یکتا در Company و دوره
- Optimistic Locking
- تراکنش اتمیک
- Tenant/Company/Branch isolation

**متن گوینده:**

دو کاربر نباید بتوانند یک عملیات را دوبار ثبت کنند یا یک شمارهٔ قطعی یکسان بگیرند. شناسهٔ idempotency، قفل خوش‌بینانه و تراکنش اتمیک برای این موضوع لازم است. باجه زیرمجموعهٔ شعبه است و شعبه زیرمجموعهٔ Company؛ این مرز در RLS و گزارش‌ها حفظ می‌شود.

## اسلاید ۶ — ایجنت‌ها چگونه کار می‌کنند؟

**متن روی اسلاید:**

```text
Event → Outbox → Agent Worker → Finding → کارتابل مدیر
```

- Accounting Review
- Document/OCR Review
- Compliance Review
- Ledger Integrity
- Anomaly Review
- Daily Manager Report

**متن گوینده:**

پس از ایجاد یا Posting سند، Event در Outbox ثبت می‌شود. Worker ایجنت‌ها را با correlation ID و نسخهٔ سند اجرا می‌کند. هر ایجنت evidence، confidence، Rule Version و اقدام پیشنهادی برمی‌گرداند. خروجی در Finding ذخیره می‌شود و هیچ ایجنتی مستقیماً Journal نهایی را تغییر نمی‌دهد.

## اسلاید ۷ — اخطار غیرمسدودکننده

**متن روی اسلاید:**

- INFO
- WARNING
- HIGH_RISK
- BLOCKING فقط برای Domain قطعی

**متن گوینده:**

اگر پیوست فاکتور وجود ندارد یا شناسهٔ فروشنده با OCR همسان نیست، کاربر اخطار می‌گیرد و مدیر آن را در کارتابل می‌بیند. سند در وضعیت مناسب باقی می‌ماند و کار متوقف نمی‌شود. اما جمع بدهکار و بستانکار نابرابر، دورهٔ بسته یا حساب گروهی در Posting، خطای قطعی است و باید متوقف شود.

## اسلاید ۸ — بررسی دفاتر

**متن روی اسلاید:**

- Journal منبع حقیقت
- Projection برای روزنامه، کل، معین و تفصیلی
- Reconciliation روزانه
- Retry و Dead Letter
- بدون اصلاح خودکار Ledger

**متن گوینده:**

دفاتر از Journal قابل بازسازی‌اند. پس از Posting، Projection به‌روزرسانی می‌شود. ایجنت کنترل دفتر جمع‌ها و hash را مقایسه می‌کند و اگر اختلافی باشد finding می‌سازد. سیستم به‌صورت خودکار دفتر نهایی را اصلاح نمی‌کند؛ اصلاح باید از مسیر فنی و قابل حسابرسی انجام شود.

## اسلاید ۹ — ارز و ریال/تومان

**متن روی اسلاید:**

- IRR به‌عنوان ریال
- IRT برای ورود یا نمایش طبق Policy
- Amount دقیق، بدون float
- نرخ با جهت صریح
- Snapshot نرخ در سند

**متن گوینده:**

مبلغ، ارز، scale، نرخ و سیاست گردکردن باید با هم ثبت شوند. نرخ باید بگوید یک واحد ارز پایه چند واحد ارز مظنه است؛ مثلاً یک دلار چند ریال. نرخ روز آینده نباید سند گذشته را تغییر دهد. سند Posted با snapshot نرخ تاریخی خود باقی می‌ماند.

## اسلاید ۱۰ — چندنرخی و تسعیر

**متن روی اسلاید:**

- نرخ حسابداری
- نرخ گمرکی
- نرخ مالیاتی
- نرخ قرارداد
- نرخ بانک و تسویه
- realized و unrealized جدا

**متن گوینده:**

یک معامله ممکن است نرخ گمرکی، نرخ قرارداد، نرخ حسابداری و نرخ تسویه داشته باشد. این اعداد نباید در یک ستون مخلوط شوند. در پایان دوره، اقلام پولی باز با نرخ پایان دوره بازسنجی می‌شوند. تفاوت تحقق‌نیافته از تفاوت تحقق‌یافتهٔ زمان تسویه جدا گزارش می‌شود.

## اسلاید ۱۱ — واردات و صادرات

**متن روی اسلاید:**

واردات: پروفرما → حمل → گمرک → هزینه‌های جانبی → انبار → پرداخت
صادرات: قرارداد → حمل → اظهارنامه → شناسایی درآمد → دریافت → تسعیر

**متن گوینده:**

در واردات، ارزش کالا، حمل، بیمه، حقوق و عوارض، مالیات و هزینهٔ ترخیص باید جدا ثبت و به موجودی یا دارایی تخصیص‌پذیر باشند. در صادرات، شناسایی درآمد را نباید صرفاً با دریافت وجه یکی دانست. ارتباط اسناد حمل، اظهارنامه، دریافت و نرخ تسویه باید قابل ردیابی باشد.

## اسلاید ۱۲ — همکاری چند همکار و ایجنت

**متن روی اسلاید:**

```text
Issue → Study → Branch → PR → Review → Merge → Handover
```

- مطالعهٔ اجباری کار قبلی
- ثبت پرسش در Issue/دفتر همکاری
- مسئول پاسخ مشخص
- شواهد پاسخ یا اصلاح
- پرسش باز در کارتابل مدیر

**متن گوینده:**

هیچ همکاری نباید بدون مطالعهٔ Changelog، ADR، PR و فایل‌های مرتبط شروع کند. اگر همکار دوم ابهامی دید، پرسش را به commit یا PR مربوط متصل می‌کند. همکار ایجادکننده موظف به پاسخ یا اصلاح است. پرسش بدون شواهد بسته نمی‌شود. همین قاعده برای AI Agentها نیز اعمال می‌شود.

## اسلاید ۱۳ — ساختار Schema، بدون اجرای فعلی

**متن روی اسلاید:**

- currencies
- exchange_rates
- rate_sources / rate_types
- document_rate_snapshots
- journal_lines با مبلغ ارزی و پایه
- fx_revaluation_runs / lines
- fx_settlement_differences
- import_cases / export_cases

**متن گوینده:**

این‌ها طراحی منطقی هستند، نه Migration اجراشده. پیش از اجرا باید ارز عملکردی Company، تعریف تومان، انواع نرخ مجاز، حساب‌های تسعیر، سیاست واردات و صادرات، RLS، backup و rollback تأیید شوند.

## اسلاید ۱۴ — نقشه‌راه اجرایی

**متن روی اسلاید:**

- F0: Domain و invariantها
- F1: Workflow سند و Posting
- F2: Persistence، RLS و دفاتر
- F3: ارز، Dimensions و FX
- F4: Reconciliation و API
- F5: Sales، Purchase، Inventory و Compliance

**متن گوینده:**

ابتدا باید قراردادهای Domain و تست‌های آن‌ها سبز شود. سپس Workflow و Posting ساخته می‌شود. بعد از تأیید مالک، Persistence و RLS وارد می‌شوند. ارز و تسعیر پس از تثبیت Ledger می‌آیند. Compliance و اتصال‌های بیرونی روی قراردادهای پایدار قرار می‌گیرند.

## اسلاید ۱۵ — تصمیم‌های موردنیاز مدیریت

**متن روی اسلاید:**

۱. تأیید Company/Branch به‌عنوان مرز سازمانی و عملیاتی
۲. تأیید اخطارهای مقرراتی غیرمسدودکننده
۳. تأیید IRR و Policy ورود تومان
۴. انتخاب انواع نرخ مجاز
۵. تعیین نقش‌های Approve و Post
۶. تصویب یا رد ورود به طراحی Migration

**متن گوینده:**

در این مرحله از مدیریت مجوز اجرای Migration نمی‌خواهیم. ابتدا تصمیم‌های محصول و Policy روشن می‌شود. سپس طرح دیتابیس، RLS، Backup، Restore و تست‌ها در PR جداگانه ارائه خواهد شد.

## اسلاید ۱۶ — پیام نهایی

**متن روی اسلاید:**

**هوش مصنوعی پیشنهاد می‌دهد؛ Domain کنترل می‌کند؛ انسان تصمیم حساس را تأیید می‌کند؛ Ledger حقیقت قابل حسابرسی را نگه می‌دارد.**

**متن گوینده:**

معماری پیشنهادی سرعت باجه را با کنترل حسابداری جمع می‌کند. کاربر متوقف نمی‌شود مگر در خطای قطعی. مدیر تصویر روزانه و قابل پیگیری دارد. همکاران و ایجنت‌ها مسیر ثبت‌شده و قابل بازبینی دارند. و هر تغییر مهم قبل از ورود به Database یا مقررات، از مسیر حاکمیت پروژه عبور می‌کند.
