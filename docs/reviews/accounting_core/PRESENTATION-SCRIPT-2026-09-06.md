## اسلاید ۵ — Proposal راهنمای استانداردها

**هدف Proposal:** ایجاد یک catalog قابل‌نسخه‌بندی از قواعد راهنما برای:

- استانداردهای حسابداری؛
- استانداردهای حسابرسی؛
- قوانین و بخشنامه‌های مالیاتی؛
- طبقه‌بندی و الزامات صورتحساب الکترونیکی.

**اصل مهم:** این سرویس در فاز اول **پیشنهاددهنده و هشداردهنده** است، نه قفل‌کننده ثبت سند.

**متن گوینده:**

ماژول پیشنهادی باید به کاربر بگوید چه قاعده‌ای ممکن است به تراکنش مربوط باشد، منبع آن چیست و اعتبار آن تا چه تاریخی است. این راهنما جایگزین حسابدار، حسابرس یا مشاور مالیاتی نیست و نباید بدون منبع رسمی، متن مقررات تولید کند.

## اسلاید ۶ — سلسله‌مراتب منابع رسمی

**ترتیب پیشنهادی اعتماد:**

1. متن قانون و مقررات در [سامانه ملی قوانین و مقررات جمهوری اسلامی ایران](https://qavanin.ir/).
2. استانداردها و نشریات منتشرشده توسط [سازمان حسابرسی](https://www.audit.org.ir/) یا مرجع رسمی تعیین‌شده برای استانداردگذاری.
3. قوانین، بخشنامه‌ها و اطلاعیه‌های [سازمان امور مالیاتی کشور](https://www.intamedia.ir/) و درگاه بخشنامه‌های مالیاتی [inta.tax.gov.ir](https://inta.tax.gov.ir/Pages/Action/LastDocs/1).
4. مستندات رسمی سامانه مؤدیان و schema/code listهای اعلام‌شده توسط مرجع مالیاتی.
5. منابع حرفه‌ای ثانویه فقط برای discovery؛ هر قاعده پیش از ورود به catalog باید با منبع اولیه تطبیق داده شود.

**کنترل اجباری برای هر قاعده:**

`source_authority`، `source_reference`، URL رسمی، تاریخ دسترسی، تاریخ اجرا، تاریخ انقضا، نسخه، وضعیت اعتبار و checksum یا فایل بایگانی منبع.

**یادداشت مهم:** برخی صفحات رسمی در زمان بررسی دسترسی پایدار یا محتوای قابل‌استخراج نداشتند. بنابراین معرفی URL به معنی تأیید متن مقررات یا کامل‌بودن منبع نیست؛ ورود به catalog فقط پس از دریافت سند رسمی قابل‌استناد مجاز است.

## اسلاید ۷ — پاسخ پیشنهادی به Q-2026-003: منبع رسمی قواعد چیست؟

**پاسخ پیشنهادی:**

منبع قواعد باید به‌صورت چندمرجعی اما با مالکیت مشخص تعریف شود:

| حوزه | مرجع اولیه پیشنهادی | شرط ورود به catalog |
|---|---|---|
| قوانین و مقررات | سامانه ملی قوانین و مقررات | شناسه قانون/ماده و نسخه متن |
| استاندارد حسابداری و حسابرسی | سازمان حسابرسی یا مرجع رسمی مصوب | شماره استاندارد، ویرایش و تاریخ اجرا |
| مالیات و بخشنامه‌ها | سازمان امور مالیاتی | شماره بخشنامه/اطلاعیه و URL رسمی |
| صورتحساب الکترونیکی | مستندات رسمی سازمان امور مالیاتی و سامانه مؤدیان | نسخه schema و code list رسمی |

**تصمیم معماری پیشنهادی:**

هیچ قاعده‌ای با منبع «نامشخص»، نقل‌قول بدون سند، یا متن تولیدشده توسط مدل زبانی وارد catalog فعال نشود. داده بدون منبع فقط می‌تواند در محیط آموزشی و با وضعیت `DRAFT` نگهداری شود.

**نیازمند تأیید:** نام مالک محتوا و مسئول نهایی انتشار هر نسخه در پروژه.

## اسلاید ۸ — پاسخ پیشنهادی به Q-2026-004: سطح هشدار

**پیشنهاد فاز اول:**

- `INFO`: اطلاع‌رسانی یا پیشنهاد حسابداری.
- `WARNING`: نیازمند توجه و بررسی کاربر.
- `CRITICAL`: ریسک بالا، اما هنوز غیرمسدودکننده در فاز اول.
- `BLOCKING`: فعلاً پیاده‌سازی نشود.

**دلیل:** مسدود کردن ثبت سند یک تصمیم سیاستی و حقوقی است و باید پس از تعریف فرآیند override، ثبت دلیل کاربر، سطح دسترسی، audit trail و تأیید متخصص مالی انجام شود.

**پاسخ پیشنهادی:** در MVP فقط `INFO` و `WARNING` فعال باشند. `CRITICAL` برای نمایش ریسک جدی قابل تعریف باشد، اما ثبت را مسدود نکند. هر سطح مسدودکننده به تصمیم مستقل در `DECISIONS.md` نیاز دارد.

## اسلاید ۹ — پاسخ پیشنهادی به Q-2026-005: JSON یا SQLite؟

**پیشنهاد مرحله‌ای:**

- فاز اول: فایل JSON نسخه‌بندی‌شده و قابل بازبینی در Git برای catalog اولیه.
- دسترسی به داده از طریق `IStandardCatalogRepository` یا Port مستقل.
- اعتبارسنجی schema، شناسه یکتا، بازه اعتبار و وجود منبع رسمی قبل از فعال‌سازی.
- فاز عملیاتی: انتقال همین Port به SQLite/PostgreSQL با migration رسمی.
- محتوای فعال از داده‌های immutable یا audit‌شده تولید شود؛ ویرایش مستقیم رکورد فعال مجاز نباشد.

**پاسخ پیشنهادی:** JSON برای شروع مناسب است، چون محتوای حقوقی باید reviewable و version-controlled باشد. با رشد catalog و نیاز به چندشرکتی، جست‌وجو، مجوز و audit، persistence دیتابیسی لازم خواهد شد.

## اسلاید ۱۰ — پاسخ پیشنهادی به Q-2026-006: taxonomy فاکتور

**پاسخ پیشنهادی:**

taxonomy داخلی نباید جایگزین taxonomy رسمی صورتحساب الکترونیکی شود. مدل باید دو لایه داشته باشد:

1. `internal_invoice_type`: دسته‌بندی قابل‌فهم برای UX، مانند فروش، برگشت، صادرات یا خدمات.
2. `official_external_code`: کد یا نوع رسمی که از schema و code list مرجع مالیاتی می‌آید.

هر نگاشت باید version، منبع، تاریخ اجرا و وضعیت اعتبار داشته باشد. تا زمانی که code list رسمی و نسخه معتبر دریافت نشده، مقادیر نمونه باید با `SAMPLE` علامت‌گذاری شوند و در محیط production فعال نشوند.

### Q-2026-001 — مدیر پروژه چه کسی است؟

**پاسخ پیشنهادی:** برای تغییرات schema تولیدی، migration مستقل با شناسه، precondition، rollback یا روش restore، تست روی نسخه قدیمی و ثبت در changelog لازم است. migration ضمنی فعلی برای سخت‌سازی اولیه قابل قبول است، اما پیش از production باید به فرآیند versioned migration منتقل شود.
