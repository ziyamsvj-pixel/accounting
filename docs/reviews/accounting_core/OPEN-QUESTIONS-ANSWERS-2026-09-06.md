# پاسخ پیشنهادی به پرسش‌های باز حاکمیتی

**تاریخ:** 2026-09-06
**وضعیت:** پیشنهاد برای تصمیم‌گیری؛ این سند جایگزین approval رسمی نیست.

## Q-2026-001 — Project Manager

**پاسخ پیشنهادی:** مالک مخزن می‌تواند مسئول فنی اولیه باشد، اما نام Project Manager و مسئول نهایی تأیید محتوای مقرراتی باید صریحاً توسط مالک پروژه اعلام و در `PROJECT_POLICY.md` ثبت شود.

**تصمیم لازم:** معرفی رسمی مسئول و سطح اختیار او.

## Q-2026-002 — Versioned migrations

**پاسخ پیشنهادی:** migrationهای تولیدی باید شناسه‌دار، قابل بازبینی، قابل آزمون روی نسخه قبلی و همراه با روش restore/rollback باشند. migration ضمنی فعلی برای سخت‌سازی اولیه قابل قبول است، اما پیش از production باید به migration versioned منتقل شود.

**تصمیم لازم:** انتخاب ابزار و سیاست migration.

## Q-2026-003 — منابع رسمی مقررات

**پاسخ پیشنهادی:** منابع اولیه مجاز عبارت‌اند از [سامانه ملی قوانین و مقررات](https://qavanin.ir/)، [سازمان حسابرسی](https://www.audit.org.ir/)، [سازمان امور مالیاتی](https://www.intamedia.ir/) و درگاه بخشنامه‌های مالیاتی [inta.tax.gov.ir](https://inta.tax.gov.ir/Pages/Action/LastDocs/1). برای هر قاعده، شناسه سند، شماره ماده/بخشنامه، URL، تاریخ دسترسی، تاریخ اجرا و نسخه باید ذخیره شود.

**محدودیت:** در زمان بررسی، برخی صفحات رسمی دسترسی پایدار یا محتوای قابل‌استخراج نداشتند. بنابراین هیچ متن مقرراتی از حافظه یا منبع ثانویه وارد catalog فعال نمی‌شود.

**تصمیم لازم:** مالک محتوا، فهرست منابع مجاز و فرآیند import/review.

## Q-2026-004 — شدت هشدار

**پاسخ پیشنهادی:** در MVP فقط `INFO` و `WARNING` فعال شوند. `CRITICAL` می‌تواند برای نمایش ریسک جدی ولی غیرمسدودکننده تعریف شود. `BLOCKING` تا زمان تصویب سیاست، فرآیند override، مجوز و audit trail پیاده نشود.

**تصمیم لازم:** سیاست severity و شرایط احتمالی blocking.

## Q-2026-005 — JSON یا پایگاه‌داده

**پاسخ پیشنهادی:** فاز اول با JSON نسخه‌بندی‌شده در Git و Port مستقل شروع شود. در فاز عملیاتی، همان Port به SQLite/PostgreSQL منتقل شود. هر رکورد فعال باید immutable/versioned باشد.

**تصمیم لازم:** تأیید JSON برای MVP و معیار انتقال به persistence دیتابیسی.

## Q-2026-006 — taxonomy نوع فاکتور

**پاسخ پیشنهادی:** مدل دو لایه باشد: `internal_invoice_type` برای UX و `official_external_code` برای کد رسمی مرجع مالیاتی. هر نگاشت باید version، منبع و تاریخ اعتبار داشته باشد. مقادیر نمونه در production فعال نشوند.

**تصمیم لازم:** دریافت code list رسمی و تأیید taxonomy داخلی.

## قاعده مشترک انتشار

تا زمان پاسخ رسمی به موارد بالا، Proposal در وضعیت `Pending Approval` باقی می‌ماند و فقط تست‌های مصنوعی بدون ادعای مقرراتی مجاز هستند. هیچ قاعده‌ای بدون منبع اولیه، reviewer، نسخه و تاریخ اعتبار به catalog فعال اضافه نمی‌شود.
